19 de Novembro de 2026 - O Grupo de Desenvolvimento Global do PostgreSQL anunciou hoje o lançamento do PostgreSQL 19, a versão mais recente do banco de dados de código aberto mais avançado do mundo.

O uso do PostgreSQL em sistemas de missão crítica continua a crescer rapidamente, e o PostgreSQL 19 responde a isso simplificando tanto a administração quanto o desenvolvimento para essas cargas de trabalho em escala. Esta versão introduz o comando REPACK (CONCURRENTLY) para que os usuários possam otimizar tabelas para a sua carga de trabalho atual sem interromper as operações em andamento. O PostgreSQL 19 oferece aos usuários melhor controle sobre a estabilidade de planos e o desempenho das consultas com a nova extensão pg_plan_advice. Os desenvolvedores encontrarão muitos recursos encantadores nesta versão, desde o suporte à consistência "leia-suas-escritas" em servidores em espera até o comportamento "obter ou criar" que economiza uma ida e volta na rede.

"Por mais de 30 anos, a comunidade global de código aberto transformou o PostgreSQL em um banco de dados no qual as organizações confiam seus dados mais críticos", disse Jonathan Katz, um membro da equipe principal do PostgreSQL. "O PostgreSQL 19 dá continuidade a esse compromisso com a confiabilidade, oferecendo aos usuários novas maneiras de gerenciar suas cargas de trabalho sem interrupções e de criar aplicações que abrangem múltiplos sistemas."

PostgreSQL, um sistema inovador de gerenciamento de dados conhecido por sua confiabilidade, robustez e extensibilidade, se beneficia de 30 anos de desenvolvimento de código aberto de uma comunidade global de desenvolvedores e se tornou o banco de dados relacional de código aberto preferido por organizações de todos os tamanhos.

Simplificando o gerenciamento de cargas de trabalho

Tabelas que recebem muitas atualizações e exclusões podem acumular espaço não utilizado, conhecido como "inchaço", o que também pode impactar significativamente o desempenho das consultas. Os comandos VACUUM FULL e CLUSTER eram usados anteriormente para lidar com isso, mas tinham desvantagens, incluindo impedir o acesso à tabela até que a limpeza fosse concluída. O PostgreSQL 19 introduz o comando REPACK, que recupera esse espaço e pode reordenar os dados de uma tabela para corresponder a um índice e, com REPACK (CONCURRENTLY), pode fazê-lo sem bloquear leituras ou escritas. O REPACK substitui os comandos VACUUM FULL e CLUSTER, ambos permanecem disponíveis para compatibilidade.

O planejador de consultas do PostgreSQL geralmente escolhe um plano eficiente para cada consulta, mas o plano pode mudar à medida que seus dados mudam e, às vezes, o novo plano é mais lento. O PostgreSQL 19 adiciona a extensão pg_plan_advice, que permite a estabilização das escolhas de plano e a capacidade de experimentar diferentes planos usando a minilinguagem de "sugestão de plano". A extensão complementar pg_stash_advice armazena sugestões e as aplica automaticamente às consultas com base em seu identificador de consulta, para que você possa corrigir um plano lento sem alterar sua aplicação.

O PostgreSQL 19 também ajuda o autovacuum a acompanhar o ritmo em sistemas ocupados. O autovacuum agora pode limpar índices usando processos paralelos, controlados pela nova configuração autovacuum_max_parallel_workers, e usa um novo sistema de pontuação para decidir quais tabelas processar primeiro. Consultas que leem uma tabela agora podem marcar páginas automaticamente como totalmente visíveis no mapa de visibilidade durante a execução, reduzindo o trabalho que futuras limpezas precisam fazer. Além disso, o vacuumdb --analyze-only agora analisa tabelas particionadas quando nenhuma tabela é especificada.

Esta versão adiciona novas visões para monitorar cargas de trabalho, incluindo pg_stat_lock para estatísticas por tipo de bloqueio, pg_stat_recovery para o status da recuperação e pg_stat_autovacuum_scores para mostrar como o autovacuum prioriza as tabelas. A nova opção IO do EXPLAIN ANALYZE e a configuração correspondente do auto_explain informam a atividade de I/O assíncrona. O PostgreSQL 19 também informa a quantidade de WAL gravada para imagens de página inteira em pg_stat_wal, EXPLAIN (ANALYZE, WAL) e em eventos de log de limpeza e análise.

Melhorias em dados distribuídos

Anteriormente, o PostgreSQL frequentemente exigia que os usuários reiniciassem o servidor para habilitar a replicação lógica, o que podia ser disruptivo em cargas de trabalho de produção. O PostgreSQL 19 simplifica a inicialização da replicação lógica elevando automaticamente o nível efetivo do WAL para logical quando você cria o primeiro slot de replicação lógica. Você pode ver o nível do WAL em uso com a nova configuração effective_wal_level.

O PostgreSQL 19 também adiciona a replicação lógica de valores de sequências, que você pode publicar usando FOR ALL SEQUENCES com CREATE PUBLICATION. O CREATE PUBLICATION também adiciona uma cláusula EXCEPT para excluir tabelas ao publicar FOR ALL TABLES, e o CREATE SUBSCRIPTION agora pode obter suas configurações de conexão de um servidor externo, como um definido com postgres_fdw, usando a cláusula SERVER. Além disso, a nova opção de subscrição retain_dead_tuples permite que o PostgreSQL detecte atualizações que conflitam com uma exclusão concorrente, e esses conflitos são contabilizados em pg_stat_subscription_stats.

Para aplicações que enviam leituras a servidores em espera, o PostgreSQL 19 adiciona a consistência "leia-suas-escritas" com o novo comando WAIT FOR LSN. Uma sessão em um servidor em espera pode usar WAIT FOR LSN para esperar até que o servidor em espera tenha aplicado o log de transação (WAL) até um número de sequência do log (LSN) específico antes de executar uma consulta, para que a aplicação possa ler os dados que acabou de gravar no primário.

O PostgreSQL 19 também melhora as consultas em tabelas externas. Com a nova opção import_stats, o postgres_fdw pode importar estatísticas de tabela do servidor remoto quando você executa ANALYZE, em vez de amostrar linhas da tabela remota, o que ajuda o planejador de consultas a escolher planos melhores.

Melhorias na experiência do desenvolvedor e no desempenho

O PostgreSQL 19 adiciona o INSERT ... ON CONFLICT DO SELECT, que permite que a cláusula RETURNING retorne linhas existentes que conflitam com uma inserção, simplificando o padrão comum "obter ou criar". O COPY agora pode gerar dados como JSON, inclusive como uma única matriz JSON, e a linguagem de caminho SQL/JSON adiciona métodos de cadeia de caracteres como lower(), upper(), replace(), split_part() e btrim(). Além disso, as funções de janela deslizante lead(), lag(), first_value(), last_value() e nth_value() agora podem ignorar valores NULL usando IGNORE NULLS. A função random() agora também pode gerar datas e timestamps aleatórios dentro de um intervalo.

Esta versão também torna muitas cargas de trabalho mais rápidas sem alterações na sua aplicação. O PostgreSQL 19 melhora o desempenho das verificações de chave estrangeira, o que, em testes, tornou as inserções em massa quase 2x mais rápidas, e adiciona mais otimizações do planejador de consultas, como a conversão de cláusulas NOT IN em anti-junções mais eficientes quando não há valores NULL presentes, e a realização de agregação antecipada antes das junções para reduzir o número de linhas a processar. O PostgreSQL 19 também se baseia no subsistema de I/O assíncrona adicionado no PostgreSQL 18. Quando io_method está definido como worker (o padrão), o PostgreSQL agora ajusta automaticamente o número de processos de I/O entre as novas configurações io_min_workers e io_max_workers, que substituem a configuração io_workers. Há também melhorias de escalabilidade ao usar LISTEN e NOTIFY para trocar notificações em cargas de trabalho de múltiplos canais.

Por fim, a nova configuração password_expiration_warning_threshold avisa os usuários quando a senha está prestes a expirar.

Outras mudanças notáveis

O PostgreSQL 19 adiciona suporte do lado do servidor para Server Name Indication (SNI), permitindo que um único servidor PostgreSQL apresente um certificado TLS diferente com base no nome de máquina ao qual um cliente se conecta. Você pode mapear nomes de máquina para seus certificados e chaves no novo arquivo pg_hosts.conf. O PostgreSQL 19 agora também emite um aviso após uma autenticação de senha md5 bem-sucedida, que você pode desativar com a configuração md5_password_warnings. A autenticação de senha md5 foi descontinuada no PostgreSQL 18 e será removida em uma versão futura. Se você precisar de autenticação baseada em senha, use a autenticação SCRAM. Esta versão também remove o suporte para autenticação RADIUS.

A compilação Just-in-time (JIT) agora está desabilitada por padrão, já que as estimativas de custo que o PostgreSQL usava para decidir quando utilizá-la se mostraram não confiáveis. Se você executa muitas consultas analíticas grandes, talvez queira habilitar o JIT. Quando o PostgreSQL é compilado com suporte a LZ4, o método de compressão TOAST padrão agora é lz4.
